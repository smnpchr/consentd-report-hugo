# consentd-reports

Hugo-based report viewer for consentd consent synchronisation reports.

## What is consentd?

consentd is a consent synchronisation engine used in the German university
medicine initiative (MII). It synchronises patient biobank consent
decisions between two systems:

- **THS** — a trust center that manages patient consent declarations.
  Patients consent (or decline) to biobank-related activities like
  specimen collection, retrospective usage, or non-EU data transfer.
- **LIMS** — the local laboratory information system that manages
  biospecimens. It needs to know the consent status to handle specimens
  correctly.

consentd runs as a scheduled daemon that periodically queries the THS for
consent status, compares it with the current LIMS state, evaluates
declarative YAML rules to decide what to do (import, invalidate, report),
and executes the resulting actions.

Each consent covers four modules:
- Acquire, use and stock specimens (base consent)
- Additional specimen acquisition
- Retrospective usage of existing specimens
- Non-EU/GDPR-level data transfer

The consent is "consistent" when the module decisions are logically
coherent — e.g. if the base consent is declined, extension modules
cannot be accepted.

### Rule engine

consentd uses a first-match rule engine with YAML-defined rules. Each rule
describes a constellation (THS status, LIMS status, recency, equality)
and the actions to take (import, invalidate, report).

### Reporting

After each sync run, consentd generates Markdown reports — one per
patient evaluation — containing the matched rule, the consent comparison
between THS and LIMS, and the executed actions. These reports are the
content source for this Hugo site.

Reports have four severity levels: info (normal operation), warning
(anomaly worth noting), error (data problem), and critical (action
execution failure).

## Purpose

Renders daily consent sync reports as a navigable static site.
Reports are generated by consentd's `Md`-Builder (Java) and placed
into `content/reports/` as Markdown files with minimal front matter.

## Architecture

- **Theme**: Hugo Book (minimal, hierarchical sidebar navigation)
- **Content source**: Markdown files generated by consentd
- **No build tooling**: No npm, no PostCSS — plain Hugo
- **Deployment**: `hugo` builds to `public/`, served via nginx or file://

## Content Structure

Four section levels under `content/reports/`: **sync type → sync run →
evaluation stage → patient detail**. Each sync type (`daily`, `weekly`,
more may be added) is a flat top-level section (`bookFlatSection`) holding
its runs; each sync run is named by `sync.title()` (a date, a week label);
stages (`import`, `operational`, `compare`) are the leaf summaries that
directly hold the patient comparisons.

```
content/
├── _index.md                          # Landing page
└── reports/
    ├── _index.md                      # Reports overview (lists sync types)
    ├── daily/                         # Sync type — flat section (bookFlatSection)
    │   ├── _index.md                  # Sync-type index (title + weight)
    │   └── 2026-05-19/                # Sync run — titled by date
    │       ├── _index.md              # Sync-run index (structural node)
    │       ├── import/                # Evaluation stage
    │       │   ├── _index.md          # Stage index (bookIcon + severity counters)
    │       │   ├── int-affirmed.md    # Patient detail
    │       │   └── int-import-fail.md
    │       └── operational/
    │           ├── _index.md
    │           ├── int-declined.md
    │           └── int-update.md
    └── weekly/                        # Sync type — flat section
        ├── _index.md
        └── 2026-week-21/              # Sync run — "Woche 21 Report"
            ├── _index.md
            └── compare/               # COMPARE stage
                ├── _index.md
                ├── int-compare-equal.md
                └── int-compare-drift.md
```

### Sidebar Behavior

- Each sync type is a flat section (`bookFlatSection`); its runs appear
  directly under it without an extra collapsible level
- Each sync run is a collapsible chapter; each stage a collapsible
  sub-chapter carrying its `bookIcon` (`import` / `operational` /
  `compare`, served from `assets/icons/`)
- The application surfaces the freshest content by emitting
  `bookCollapseSection: false` on the most recent run and its primary
  stage (latest daily's `import`, latest weekly's `compare`), so they
  render expanded by default; older runs keep `true` and stay collapsed
- Patient entries appear as child items under their stage when expanded
- Patient entries are color-coded by severity via CSS class
- Clicking a patient shows the full evaluation detail

## Front Matter Convention

All structured data lives in front matter; the Markdown body is minimal
(typically just an H1). The Hugo templates render evaluation, consent
comparison, rule spec, and actions entirely from `.Params`. See
`docs/front-matter-convention.md` for the full schema and enum values.

Field names are camelCase (matching the Java record components in
`HugoBookGenerator`). The side-by-side comparison is direction-neutral:
front matter speaks of `source` / `target`, not `ths` / `lims`. THS,
CentraXX etc. survive only as concrete `InstanceName` values
(`sourceName`, `targetName`, `consent.*.origin`) and inside rule
*identifiers* (`NEW_AFFIRMED_THS`) — those are not "corrected". Enum
values are emitted as their Java form (`AFFIRMED`, `INCONSISTENT`,
`GRANTED`, etc.); human-readable labels live in `i18n/de.yaml`.

### Sync-Run Index (`_index.md` in sync-run folder)

Structural node, written once per sync run. No aggregates — those live on
the stage indexes below.

```yaml
---
title: "19.05.2026"
date: 2026-05-19T18:30:00+02:00
weight: 20260519
bookCollapseSection: true
---
```

### Stage Index (`_index.md` in stage folder)

Written once per stage. Carries the `bookIcon` and the severity
aggregates; this is also the leaf summary that renders the patient table.
No `title` — Hugo derives `.Title` from the folder name (`import` →
"Import").

```yaml
---
date: 2026-05-19T18:30:00+02:00
weight: 20260519
bookCollapseSection: true
bookIcon: import
patientCount: 5
severityInfo: 2
severityWarning: 2
severityError: 1
severityCritical: 0
---
```

| Field | Used by |
|-------|---------|
| `title` | (sync-run only) sidebar, page title |
| `date` | Hugo sort order |
| `weight` | Sidebar ordering (newest first) |
| `bookCollapseSection` | Hugo Book collapsible sidebar section |
| `bookIcon` | (stage only) stage icon via `docs/icon` partial |
| `patientCount` | (stage only) summary page heading, reports overview |
| `severityInfo`, `severityWarning`, `severityError`, `severityCritical` | (stage only) counter badges on summary page |

Body: minimal — typically `# {title}` (sync run) or empty (stage).

### Patient Detail (leaf page)

The leaf page front matter is a 1:1 Jackson serialization of the Java
domain records — `rule` (DecisionRule), `evaluation` (RuleEvaluation),
`consent` (source + target BioBankConsent), optional `failureInfo`.
Top-level `severity` drives the banner; `sourceName` / `targetName` name
the sync endpoints (drive the comparison column headers); the nested
objects feed the detail tables.

See `docs/front-matter-convention.md` for the canonical schema, field
tables, and the full enum value lists. Example fixtures live in
`content/reports/daily/2026-05-19/` (IMPORT + OPERATIONAL) and
`content/reports/weekly/2026-week-21/` (COMPARE).

Body: minimal — typically `# {patientId}`.

## Severity Color Scheme

| Severity | CSS class | Color | Meaning |
|----------|-----------|-------|---------|
| success | `.severity-success` | Green | Action executed successfully (e.g. consent imported) |
| info | `.severity-info` | Blue | Informational only, no action required |
| warning | `.severity-warning` | Orange | Anomaly reported |
| error | `.severity-error` | Red | Data problem (e.g. inconsistent THS) |
| critical | `.severity-critical` | Dark red | Action failed (e.g. LIMS unreachable) |

## Theme Customization Rules

### Sidebar
- Sync runs sorted newest-first (by `weight`); stages collapse under them with their `bookIcon`
- Patient entries show colored dot/icon based on `severity` param
- Stage summary pages show severity counter badges

### Detail Pages
- Severity banner at top (colored bar with icon), rendered from `severity` + `rule.name`
- Rule section: `rule.name` + `rule.description`
- Comparison column headers resolve from `sourceName` / `targetName` via `instance_<NAME>` i18n keys, falling back to generic `label_source` / `label_target`
- Evaluation table: rendered from `evaluation.sourceEvaluation` / `evaluation.targetEvaluation` against `rule.source` / `rule.target`; aggregated and timeValidity values rendered as styled badges; affirmations and content sub-sections shown only when the rule specifies `affirmed` or `content` maps
- Consent comparison table: rendered from `consent.source` and `consent.target`
- Actions list: rendered from `rule.actions`; the entry matching `failureInfo.failureAction` gets `.action-failed`
- Failure banner (only when `failureInfo` is set)
- All German labels resolved via `i18n/de.yaml` — module keys exist in both camelCase (POJO fields) and ALL_CAPS (Java enum map keys)
- No JavaScript required for detail pages

### CSS Variables (to be defined in custom CSS)
```css
:root {
  --severity-success: #16a34a;
  --severity-info: #2563eb;
  --severity-warning: #ca8a04;
  --severity-error: #dc2626;
  --severity-critical: #991b1b;
}
```

## Workflow

1. consentd runs daily sync, Md-Builder writes reports to `content/reports/`
2. `hugo` rebuilds the site
3. Nginx serves the static output

## Development

```bash
hugo server -D    # Local preview with drafts
hugo              # Build to public/
```

## What NOT to do

- Do not add JavaScript for content rendering — Hugo and CSS handle it
- Do not modify generated Markdown files — they are overwritten on next sync
- Do not put report data in the Markdown body — all structured data lives in front matter, the body is just a minimal H1
- Do not put HTML or Hugo shortcodes in generated content — the Md-Builder emits YAML front matter only
- Do not hardcode German labels in templates — add a key to `i18n/de.yaml` and reference it via `{{ i18n "..." }}`
