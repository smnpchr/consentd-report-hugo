# consentd-reports

Hugo-based report viewer for consentd consent synchronisation reports.

## What is consentd?

consentd is a consent synchronisation engine used in the German university
medicine initiative (MII). It synchronises patient biobank consent
decisions between two systems:

- **THS** — a trust center that manages patient consent declarations.
  Patients consent (or decline) to biobank-related activities like
  specimen collection, retrospective usage, or non-EU data transfer.
- **LIMS** — the local laboratory information system that manages
  biospecimens. It needs to know the consent status to handle specimens
  correctly.

consentd runs as a scheduled daemon that periodically queries the THS for
consent status, compares it with the current LIMS state, evaluates
declarative YAML rules to decide what to do (import, invalidate, report),
and executes the resulting actions.

Each consent covers four modules:
- Acquire, use and stock specimens (base consent)
- Additional specimen acquisition
- Retrospective usage of existing specimens
- Non-EU/GDPR-level data transfer

The consent is "consistent" when the module decisions are logically
coherent — e.g. if the base consent is declined, extension modules
cannot be accepted.

### Rule engine

consentd uses a first-match rule engine with YAML-defined rules. Each rule
describes a constellation (THS status, LIMS status, recency, equality)
and the actions to take (import, invalidate, report).

### Reporting

After each sync run, consentd generates Markdown reports — one per
patient evaluation — containing the matched rule, the consent comparison
between THS and LIMS, and the executed actions. These reports are the
content source for this Hugo site.

Reports have four severity levels: info (normal operation), warning
(anomaly worth noting), error (data problem), and critical (action
execution failure).

## Purpose

Renders daily consent sync reports as a navigable static site.
Reports are generated by consentd's `Md`-Builder (Java) and placed
into `content/reports/` as Markdown files with minimal front matter.

## Architecture

- **Theme**: Hugo Book (minimal, hierarchical sidebar navigation)
- **Content source**: Markdown files generated by consentd
- **No build tooling**: No npm, no PostCSS — plain Hugo
- **Deployment**: `hugo` builds to `public/`, served via nginx or file://

## Content Structure

```
content/
├── _index.md                          # Landing page
└── reports/
    ├── _index.md                      # Reports overview
    ├── 2026-05-19/                    # One sync run per day
    │   ├── _index.md                  # Daily summary
    │   ├── int-affirmed.md            # Patient detail
    │   ├── int-declined.md
    │   └── int-import-fail.md
    └── 2026-05-20/
        ├── _index.md
        └── ...
```

### Sidebar Behavior

- Each date folder is a collapsible chapter in the sidebar
- Patient entries appear as child items when expanded
- Patient entries are color-coded by severity via CSS class
- Clicking a patient shows the full evaluation detail

## Front Matter Convention

Front matter carries only what the Hugo theme needs for navigation and
visual presentation. All domain detail (evaluation, consent comparison,
rule description) lives in the Markdown body.

### Daily Summary (`_index.md` in date folder)

```yaml
---
title: "19.05.2026"
date: 2026-05-19T18:30:00+02:00
weight: 20260519
bookCollapseSection: true
patient_count: 5
severity_info: 2
severity_warning: 2
severity_error: 1
severity_critical: 0
---
```

| Field | Used by |
|-------|---------|
| `title` | Sidebar, page title |
| `date` | Hugo sort order |
| `weight` | Sidebar ordering (newest first) |
| `bookCollapseSection` | Hugo Book collapsible sidebar section |
| `patient_count` | Summary page heading, reports overview |
| `severity_*` | Counter badges on summary page |

Body: plain text summary generated by Md-Builder.

### Patient Detail (leaf page)

```yaml
---
title: "INT-AFFIRMED"
date: 2026-05-19T18:30:01+02:00
severity: info
rule: NEW_AFFIRMED_THS
actions: [IMPORT, REPORT]
---
```

With action failure (severity `critical`), add:

```yaml
failure_action: IMPORT
failure_reason: "LIMS REST API returned 503: Service Unavailable"
```

| Field | Used by |
|-------|---------|
| `title` | Sidebar, page title |
| `date` | Hugo sort order |
| `severity` | Sidebar dot, severity banner, badge in patient table |
| `rule` | Severity banner, patient table |
| `actions` | Patient table |
| `failure_action` | Failure banner (only when set) |
| `failure_reason` | Failure banner (only when set) |

Body: full Markdown report (rule, evaluation, consent table, actions).

## Severity Color Scheme

| Severity | CSS class | Color | Meaning |
|----------|-----------|-------|---------|
| info | `.severity-info` | Blue | Normal import, as expected |
| warning | `.severity-warning` | Orange | Anomaly reported |
| error | `.severity-error` | Red | Data problem (e.g. inconsistent THS) |
| critical | `.severity-critical` | Dark red | Action failed (e.g. LIMS unreachable) |

## Theme Customization Rules

### Sidebar
- Date folders sorted newest-first (by `weight`)
- Patient entries show colored dot/icon based on `severity` param
- Summary pages show severity counter badges

### Detail Pages
- Severity banner at top (colored bar with icon)
- Rule name and description
- Consent comparison as Markdown table (rendered by Hugo)
- Failure section (only when `failure_action` is set)
- No JavaScript required for detail pages

### CSS Variables (to be defined in custom CSS)
```css
:root {
  --severity-info: #2563eb;
  --severity-warning: #ca8a04;
  --severity-error: #dc2626;
  --severity-critical: #991b1b;
}
```

## Workflow

1. consentd runs daily sync, Md-Builder writes reports to `content/reports/`
2. `hugo` rebuilds the site
3. Nginx serves the static output

## Development

```bash
hugo server -D    # Local preview with drafts
hugo              # Build to public/
```

## What NOT to do

- Do not add JavaScript for content rendering — Hugo and CSS handle it
- Do not modify generated Markdown files — they are overwritten on next sync
- Do not put HTML in Markdown content — the Md-Builder produces pure Markdown
- Do not use Hugo shortcodes in generated content — only in theme templates
